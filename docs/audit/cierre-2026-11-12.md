# Auditoría de cierre — Tukul (2026-11-12)

Skill: `criterios_de_cierre`. Herramientas: lectura estática + ejecución real
(local y CI). Modalidad: evaluación **de solo lectura**, más las comprobaciones
autorizadas por el usuario (crear el tag `v0.4.1` y verificar el Release).

## Dictamen

**NO APTO PARA CIERRE.**

El núcleo, la suite y la cadena de calidad están demostrados con evidencia
fuerte y reproducible (quality gate local verde, CI verde en `master`, 734
pruebas sin omisiones, cobertura 87.9 %, ruff/mypy/bandit limpios). Sin embargo,
la **reproducción real del Release introdujo un defecto confirmado de
distribución**: el binario Linux publicado en `v0.4.1` **no arranca en ninguna
distribución con glibc < 2.42**. El smoke test de CI es ciego a él porque corre
en el mismo runner que lo compiló. Bloquea el criterio «instalar sin Python para
Linux x86_64», que es una capacidad esencial comprometida y anunciada en el
README.

## Alcance evaluado

- **Propósito:** editor conversacional local de Markdown con LLM remoto opcional.
- **Capacidades esenciales:** editar/revisar/guardar artículos; conversación con
  proveedor OpenAI-compatible; contexto aprobado; persistencia y recuperación;
  diagnóstico `--health`; **distribución standalone para Linux x86_64 y Windows
  x86_64** (README «Instalar sin Python»).
- **Versión evaluada:** `0.4.1`, tag `v0.4.1` (HEAD `7fd28bc`).
- **Entornos:** Linux/Debian (glibc 2.41) con Python 3.12/3.13 + Tk + Xvfb;
  runners de CI `ubuntu-26.04` (glibc 2.42) y `windows-latest`.
- **Nivel de madurez esperado:** Operativo controlado.

## Hallazgos y bloqueos

### DF-C1 — [ALTA · CONFIRMADO · BLOQUEA] El binario Linux publicado no arranca en glibc < 2.42

- **Capacidad afectada:** distribución standalone para Linux x86_64 (README
  «Instalar sin Python»), criterios 8, 9, 13 y 16.
- **Evidencia:**
  - Release `v0.4.1` (assets: `tukul-linux-x86_64`, `tukul-windows-x86_64.exe`,
    `SHA256SUMS`, `sbom.cdx.json`). `sha256sum -c SHA256SUMS` → ambas sumas
    coinciden.
  - Ejecución del binario descargado en host con glibc **2.41**:
    `ImportError: .../libtcl8.6.so: version 'GLIBC_2.42' not found` → exit 1.
  - Log del run `43348367772`: runner `ubuntu-26.04`, glibc **2.42**. El smoke
    `--health` pasa porque corre en el **mismo** runner que lo compiló.
  - **Regresión probada:** el binario `v0.3.2` (compilado en imagen antigua)
    **sí arranca** en este mismo host (glibc 2.41, exit 0).
- **Causa raíz:** `ubuntu-latest` avanzó a Ubuntu 26.04 (glibc 2.42);
  PyInstaller empaqueta la `libtcl8.6.so` del sistema (2.42) y el binario exige
  esa glibc. El smoke test no detecta el exceso de requisito por correr en el
  mismo entorno de build.
- **Impacto:** el binario Linux es inejecutable en Debian 13, Ubuntu 24.04,
  RHEL/Rocky 9, Linux Mint 22 y en general en cualquier distro anterior a
  Ubuntu 26.04 — la mayoría del parque actual.
- **Condición de bloqueo:** **sí** — alto, afecta una función esencial
  comprometida y anunciada, sin aceptación explícita del riesgo.
- **Acción mínima esperada:** compilar en una imagen de runner más antigua
  (pin `runs-on: ubuntu-22.04` o `ubuntu-24.04`, glibc 2.35/2.39) para fijar el
  suelo de glibc, o documentar el requisito real y degradar el anuncio del
  README. Añadir una comprobación que detecte el requisito excesivo.
- **Evidencia de aceptación requerida:** descargar el nuevo `tukul-linux-x86_64`
  y ejecutar `--health` (exit 0) en un host con glibc < 2.42, más
  `sha256sum -c SHA256SUMS` en verde.

### DF-C2 — [BAJA · CONFIRMADO · NO BLOQUEA] Referencias a un archivo de tests ya dividido

- **Capacidad afectada:** documentación (criterio 14).
- **Evidencia:** `docs/SECURITY.md` cita `tests/test_auditoria_regresion.py`;
  `docs/audit/aviso-health-instalacion-virgen-2026-11-05.md` cita
  `tests/test_auditoria_regresion.py::test_instalacion_nueva_...`. El archivo se
  dividió en 6 por dominio (`reparacion-2026-11-12.md`, S1); la clase
  `TestSeguridadDelEndpoint` vive hoy en `tests/test_seguridad_red_regresion.py`.
- **Impacto operativo:** un revisor no encuentra el test citado. Sin impacto en
  ejecución.
- **Condición de bloqueo:** no.
- **Acción mínima:** actualizar la ruta citada en `docs/SECURITY.md`.

### DF-C3 — [INFORMATIVO] Windows no verificado en destino

- El binario Windows pasó el smoke `--health` en `windows-latest` y su checksum
  verifica, pero no se ejecutó en un Windows real fuera del runner.
- **Evidencia estática (2026-11-12):** el `.exe` de `v0.4.2` es `PE32+` x86-64
  (subsistema consola); su bootloader importa **solo** `USER32.dll`,
  `KERNEL32.dll` y `ADVAPI32.dll` (DLL del núcleo de Windows); empaqueta su
  propio runtime (`python312.dll`, `VCRUNTIME140.dll`, `ucrtbase.dll`, API sets
  `api-ms-win-crt-*`, `tcl86t.dll`/`tk86t.dll`, OpenSSL, SQLite). No exige
  Python, Tcl/Tk ni VC++ Redistributable en el equipo destino. `SHA256SUMS`
  coincide. Esto **rebaja el riesgo a bajo** (el análogo de DF-C1 —dependencia
  del runtime del sistema de build— está mitigado en Windows porque todo el
  runtime va empaquetado).
- **Procedimiento de cierre:** `docs/audit/verificacion-windows-df-c3.md`
  (descarga + checksum + `--health` + GUI + llavero + persistencia en un equipo
  Windows 10/11 real). No bloquea por sí solo; queda como riesgo no verificado
  hasta ejecutarlo.

## Riesgos aceptados y pendientes

- **S1 — binarios sin firma/notarización:** riesgo aceptado conscientemente
  (`docs/RELEASE.md`, `hallazgos-abiertos-2026-11-04.md#s1`). Se mantiene: la
  integridad depende del canal HTTPS y de `SHA256SUMS` (verificado en `v0.4.1`).
- **H2 — refactor de `app.py`:** mejora opcional, fuera de contrato. No bloquea.
- **Cuotas de proveedor en uso sostenido:** no verificado; no bloquea al nivel
  Operativo controlado.

## Mejoras fuera del cierre

- Extracción de `app.py` (H2) para bajar de 2.300 líneas.
- Firma/notarización (S1) cuando exista decisión de mecanismo y gestión de
  secretos.
- Prueba de accesibilidad con AT-SPI real.

## Condiciones de cierre

1. Corregir DF-C1 (pin de imagen de runner o ajuste documentado del requisito)
   y **verificar el binario Linux en un host glibc < 2.42**.
2. Confirmar `sha256sum -c SHA256SUMS` del nuevo Release.
3. Corregir DF-C2 (ruta del test en `docs/SECURITY.md`).
4. Reconocer o mitigar DF-C3 (prueba en Windows real).

## Recomendación final

Reabrir la corrección de distribución: fijar el suelo de glibc del binario Linux
y volver a publicar, verificando el ejecutable fuera del runner de CI. No
congelar la versión ni declarar cerrado el alcance hasta que el binario Linux
arranque en una distribución soportada. El resto del proyecto (código, pruebas,
seguridad, persistencia, documentación de contratos) está en condiciones de
cierre; el bloqueo es exclusivamente de empaquetado/distribución.
